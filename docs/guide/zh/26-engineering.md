# 工程：CI、议题、依赖和故障

你做别的事情的时候，智能体可以替你照看代码库：排查失败的 CI 运行、给每个新议题分诊、让依赖保持最新、响应告警，每一项都是用一张简短的表单创建的定时任务。Git 里的**找出是哪个提交弄坏了它**会让智能体找出弄坏某样东西的那个提交，而**战役**会把一项大改动拆成几部分，由几个智能体同时完成，每个都在自己的工作树中。

![设置 → 定时任务：工程类示例](images/engineering.webp)

## 工程任务如何运作

这四个任务是[设置 → 定时任务](/settings?s=tasks)（**设置 → 智能体 → 定时任务**）里的示例，位于**从示例开始**里（按**显示全部示例**就能看到），和[**审查新的拉取请求**](/settings?s=tasks&find=Review%20new%20pull%20requests)放在一起。每个都会打开一张简短的表单；填好后，在**执行者**下选择由谁运行，然后选择**创建任务**（或者用**更多选项…** 打开完整的任务表单）。任务能做的一切，请看[定时任务](/guide/tasks)。

它们的共同点：

- **一个仓库文件夹**：智能体据以工作的、这台电脑上的仓库副本。它会读取这个副本，而任何改动都在一个新的工作树（在自己的分支上的一份独立副本）里进行，所以你自己的副本和它的分支保持原样。
- **各有一个技能**：智能体遵循一套写好的方法，也就是一个内置技能，你可以在[设置 → 技能](/settings?s=skills)中阅读和修改它：**ci-doctor**、**issue-triage**、**dependency-upgrades** 和 **incident-response**。
- **它可以做什么**：表单里的开关，例如**创建带修复的草稿拉取请求**。凡是你关掉的，智能体都会改为告诉你它本来会怎么做。它们都不会推送到默认分支、强制推送或合并。
- **Webhook**：CI 医生、议题分诊和故障响应人会在某个服务调用任务专属的地址时启动。任务创建后，它在列表里的那一行会显示地址和一个复制按钮，下面还写着要把它粘贴到那个服务的什么地方（“在 GitHub 上的仓库中：Settings → Webhooks → Add webhook…”）。创建之前，表单里也会这样说明。每个任务都有一个过滤器，只让它要处理的调用启动运行（一次失败的运行、一个新开的议题、一条不是“已解决”通知的告警）；其余的调用会得到答复，但不会启动任何东西。任务菜单里的**立即运行**（或表单里的**试运行**）不需要调用也能用，可以拿来试一试：CI 医生会拿最近一次失败的运行来处理，议题分诊会处理最近一天里还没有标签的议题，故障响应人则会检查服务现在的状况。
- **访问权限**：如果这台电脑上的 gh 命令已经登录，智能体就通过它使用 GitHub；否则通过你保险库里的密钥或已连接的应用（GitHub、GitLab、Buildkite、CircleCI、Sentry、Grafana、Datadog、Better Stack：参见[已连接的应用、密钥和工具](/guide/connections)）。需要它没有的密钥时，它会向你索要。
- **每次运行**都会用一句话报告情况如何，写在它的通知和任务的历史里，并为下一次运行留下笔记（它见过的不稳定测试、它暂缓的升级、到目前为止的故障）。需要你批准的运行会在它的会话里和[收件箱](/guide/inbox)中等你。运行开始时可能没人在旁边看着，所以对这些任务，请在**更多选项…** → **权限**下选一个让常规步骤直接进行、遇到有风险的步骤再问你的模式（**自动**），否则运行会在它的第一条命令处等你。

## CI 医生

GitHub Actions、GitLab CI、Buildkite 或 CircleCI 上的一次失败运行会唤醒一个智能体。它阅读失败作业的日志，找到第一个真正的错误，查看同一作业最近的几次运行，分辨这是偶发的不稳定还是真的失败，在工作树中复现它，然后在你允许的范围内处理，并用几行话总结。

### 如何设置

1. 在[设置 → 定时任务](/settings?s=tasks)中，选择**从示例开始**里（**显示全部示例**）的[**CI 医生**](/settings?s=tasks&find=CI%20doctor)。
2. 选好**仓库文件夹**和 **CI**：**GitHub Actions**、**GitLab CI**、**Buildkite** 或 **CircleCI**。
3. 选择它可以做什么：
   - **重新运行看起来不稳定的作业**（默认开启）：只重新运行一次，而且要有证据表明是这次运行出了问题、而不是代码有问题（超时、下载失败、已知时好时坏的测试）。
   - **创建带修复的草稿拉取请求**（开启）：遇到真正的失败时，在单独的分支上做最小的修复，并运行原先失败的测试，作为草稿留给你查看。
   - **在提交或拉取请求下评论**（关闭）：写一条简短的评论，说明原因，以及修复方法或下一步。
4. 选择**创建任务**。任务以它的 CI 命名，例如“CI doctor · GitHub Actions”。
5. 把它那一行里的地址复制到 CI 中，具体位置见地址下面那行说明：
   - **GitHub Actions**：仓库的 **Settings → Webhooks → Add webhook**；把地址填为 Payload URL，选 application/json，并在单个事件（individual events）下只勾选 **Workflow runs**。
   - **GitLab CI**：项目的 **Settings → Webhooks → Add new webhook**，只勾选 **Pipeline events**。
   - **Buildkite**：**Settings → Notification Services**，在 Webhook 那一项点 **Add**，勾选 build.finished 事件。
   - **CircleCI**：项目的 **Project Settings → Webhooks → Add Webhook**，勾选 **Workflow Completed**。

只有失败的运行才会启动它（在 GitHub 上是 conclusion 为 failure 的工作流运行；在 GitLab、Buildkite 和 CircleCI 上是状态为 failed 的运行）。每次运行都会拿到那次 CI 运行的要点（工作流、它的地址、分支、提交及其说明、拉取请求），它的一句话报告会说明是不稳定还是真的失败、原因，以及它做了什么：“不稳定：npm ci 时 registry 超时；已重新运行”，或者“真实失败：日期解析器在闰年出错；草稿拉取请求 #42”。

## 议题分诊

在 GitHub（或 Gitea）上新开的每个议题都会唤醒一个智能体来给它分诊：它阅读议题和项目的贡献指南，用仓库里已有的标签给议题加标签，换几种说法在未关闭和最近关闭的议题中查找同样的问题（并说明有多大把握），在一条友好的评论里请报告者补上报告缺少的内容（版本、步骤、日志）；如果修复小而明确，就在工作树中试着修好，并创建一个引用该议题的草稿拉取请求。

1. 选择**从示例开始**里（**显示全部示例**）的[**议题分诊**](/settings?s=tasks&find=Issue%20triage)。
2. 选好**仓库文件夹**，以及它可以做什么：**加标签**、**发表评论**和**把简单的议题试着做成草稿拉取请求**（默认全部开启）。
3. 选择**创建任务**，然后把它的地址复制到 GitHub 上仓库的 **Settings → Webhooks → Add webhook** 中，在单个事件下只勾选 **Issues**（在 Gitea 上：Issues 事件）。

只有新开的议题才会启动一次运行。智能体从不关闭、锁定、转移或删除议题（对确定重复的议题，它会加上标签，留给维护者去关闭），从不指派人员，并遵守项目允许的范围：拒绝用 AI 生成的拉取请求的项目，不会收到它的拉取请求。公开报告的安全问题不会在那里讨论：智能体会引导报告者使用项目的私下报告渠道，并立即告诉你。

## 依赖园丁

智能体每周照看一次仓库的依赖（npm、pnpm、yarn、pip、uv、poetry、cargo 和 go）：哪些过时了，哪些有安全公告。安全修复优先；然后是补丁版本、次版本和主版本的升级，每组分开处理，主版本升级从不和其他升级混在一起。每组都在自己的工作树中完成：阅读改动部分的发布说明，看有没有破坏性变更，并运行测试。会让测试失败的升级会被暂缓，原因记在任务的笔记里，这样就不会每周都重新提议。

1. 选择**从示例开始**里（**显示全部示例**）的[**依赖园丁**](/settings?s=tasks&find=Dependency%20gardener)。
2. 选好**仓库文件夹**，在**开启**下选择星期几（默认周一），在**时间**下选择几点（默认 09:00）。
3. **创建拉取请求**（开启）：每个测试通过的组各开一个草稿拉取请求，写明要点、它修复的安全公告，以及需要留意的地方。关闭时，它不推送任何东西，而是逐组报告，并附上应用这些升级的命令。
4. 选择**创建任务**。

如果这一周所有依赖都是最新的，也没有未处理的安全公告，它就保持安静。

## 故障第一响应人

来自 Sentry、Grafana、Datadog、Better Stack 或其他服务的告警会唤醒一个智能体。几分钟之内，它就会发一条通知，告诉你出了什么问题、从什么时候开始、有多严重。然后，它把错误、日志、最近的部署以及自上一个正常版本以来的改动排在同一条时间线上，找出可能的原因并给出证据，再提出最稳妥的一步，通常是回滚。没有你点头，它从不回滚、重启或部署任何东西：它会在运行的会话里用一张卡片问你；如果没人及时回答，这次运行会报告它需要你处理，命令就在那里等着。事情过去之后，在同一个会话里让它写事后复盘。

1. 选择**从示例开始**里（**显示全部示例**）的[**故障第一响应人**](/settings?s=tasks&find=Incident%20first%20responder)。
2. 选好**该服务的仓库文件夹**，以及**告警来源**：**Sentry**、**Grafana**、**Datadog**、**Better Stack** 或**其他服务**。
3. **如何回滚**（可选）：你同意后智能体可以运行的命令，例如 `kubectl rollout undo deployment/web`。留空时，它会问你怎么做。
4. 选择**创建任务**，然后按它那一行的说明，把服务的告警指向它的地址：
   - **Sentry**：**Settings → Developer Settings → Create New Integration → Internal Integration**，把地址填为 Webhook URL，并打开 **Alert Rule Action**；然后把这个集成加到你的告警规则的动作中。
   - **Grafana**：**Alerting → Contact points → Add contact point**，选择 Webhook 集成并填上地址；然后通过通知策略把告警发给它。
   - **Datadog**：**Integrations → Webhooks → New**，填上地址，并在它的 payload 中加入 `"transition": "$ALERT_TRANSITION"`；然后在你的监控器消息中提及 `@webhook-` 加上它的名称。
   - **Better Stack**：**Incidents → Integrations → Exporting data → Outgoing webhooks → Configure**，然后在 Incident 那一项点 **Add**，只选择故障被创建或重新打开时的事件。

说明问题已解决或已恢复的通知不会启动任何东西（Sentry、Grafana 和 Datadog 的这类通知由过滤器挡下）；即使有漏过来的，也只会记进任务的笔记里，不会打扰你。如果告警服务有已连接的应用，智能体会通过它读取错误和日志。

## 找出是哪个提交弄坏了它

如果某样东西在早先的版本里还正常，现在却坏了，智能体可以找出弄坏它的那个提交：它用 git bisect 试验中间的那些提交，每次把范围减半（一千个提交大约只要试十次），指出第一个出问题的提交，并解释它的改动中是哪一部分弄坏了东西、为什么。

1. 在 [Git 页面](/git)上打开仓库和它的**历史**。
2. 打开它最后一次正常时的那个提交，在它的 ⋯ 菜单中选择**找出是哪个提交弄坏了它**；或者选择列表顶部**查找提交**旁边的**找出是哪个提交弄坏了它**按钮。
3. 在**找出是哪个提交弄坏了它**表单中：
   - **正常工作的版本**：你从哪个提交打开表单，就是那个提交（有标签时显示它的标签），否则是最新的标签。可以输入任何标签、分支或提交；输入时会提示最新的几个标签。下方会显示它对应的提交，以及提交说明和多久以前，或者显示“没有这个名称的提交或标签”。
   - **出问题的版本**：默认是 `HEAD`（你所在分支上的最新提交）。
   - **出了什么问题**：用你自己的话，尽量说得准确（“把带图片的文档导出为 PDF 时失败，提示‘image too large’”）。
   - **如何检查（可选）**：一条在问题存在时会失败的命令，例如 `npm test -- export`。没有的话，智能体会自己写一个检查。
   - **执行者**：智能体，使用你上次在开始页上为它选的模型和权限。
4. 选择**开始**。要等两端都是提交、且不是同一个提交，并且填好了**出了什么问题**，才能开始。

一个新会话会立即打开，在仓库的一个新工作树中运行，所以你自己的副本保持原样。它的智能体遵循 **git-bisect** 技能：先写一个小的检查脚本（正常时以 0 退出，出问题时以 1 退出，遇到无法测试的提交以 125 退出，比如无法构建的提交），先在两端各试一次，再用它运行 `git bisect run`，然后指出第一个出问题的提交，以及其改动中弄坏东西的那一部分，通过只撤销那一个提交来证明，并提出修复建议。它不会改动你的任何分支。完成后，会话菜单 → **告一段落：先到这里**会提议移除它的工作树（参见[在工作树中工作](/guide/sessions#work-in-a-worktree)）。

搜索框（Ctrl+K）也能找到**找出是哪个提交弄坏了它**：它会为你上次用过的仓库打开这个表单。

## 战役：分成许多部分的一项大改动

战役让几个智能体同时动手，在整个代码库中完成一项大的、多半是机械性的改动（把每个包都换成新的日志库、升级框架、到处重命名某个 API）。一个主导智能体把改动拆成几部分（包、模块、文件夹），每个成员在自己的工作树中完成其中一部分，并运行它的测试。它是[集群](/guide/research#set-a-swarm-on-a-hard-problem)的第二种形式：同一个设置**集群规模**决定两者同时工作的数量。

### 发起一场战役

1. 在开始页上选择仓库的文件夹。战役需要一个 git 仓库。
2. 打开**选项**，选择**集群**，再选**战役**（“把一项大改动拆成几部分，各在一个工作树中完成”）。
3. 说明要做的改动以及怎么检查（“把每个包从 Jest 迁移到 Vitest；每个包里 npm test 都必须通过”），然后按**开始**。

这时“集群”一行显示“战役 · 同时 5 个”（你的集群规模）。和集群一样，它不会保留到你的下一个会话，深度研究和战役也不能同时打开。在同一个菜单里设的花费上限涵盖主导智能体和每个成员。定时任务的编辑器里也有同样的选择。

### 战役如何运作

1. 主导智能体先弄清楚要做的改动和检查方法，再把它拆成几个能各自独立完成和测试的部分。它把计划发到看板上：各部分的名称，按要做的顺序排列（共用的代码在前）。
2. 它为每个部分启动一个成员，同时工作的不超过你的集群规模，有成员完成了再启动下一个。每个成员都在一个新工作树里、在自己的分支上工作，这个工作树基于主导智能体的文件夹当前所在的分支创建。
3. 成员只改动自己的那一部分，运行检查，在自己的分支上提交，然后发帖把它那部分标为完成（附上分支和检查结果）或失败（附上出了什么问题）。
4. 失败的部分会带着学到的经验再试一次。如果再次失败，它就保持失败。
5. 主导智能体按合理的顺序，把完成的分支逐个合并到它工作的分支上，每合并一个就运行一次检查，并移除每个已合并部分的工作树。如果你在消息里要求拉取请求，它就改为每个部分开一个拉取请求，什么都不合并。它从不推送到默认分支。
6. 最后，它报告改了什么、哪些失败了以及原因，还有哪些需要手动完成。

如果想把整个改动放在一个单独的分支上，也为主导智能体打开文件夹菜单里的**新建工作树**：这样成员会从主导智能体的分支分出去，合并也会落在那里。

### 跟进它：横条和看板

主导智能体的会话在消息框上方有一个横条：**战役** · 起初是“正在规划各个部分”，之后是“已完成 12/40 个部分 · 2 个失败 · 3 个正在工作”，还有**排行榜**按钮。每个成员的会话也有一个横条：“所属战役”和主导会话的标题，以及**排行榜**和**主导**按钮。在侧边栏中，成员排在主导会话下面，折叠成一行，比如“40 个战役成员 · 3 个在工作”。

**排行榜**会打开**战役看板**（在手机上从屏幕底部弹出）：

- **部分**：完成了多少、失败了多少，然后按计划的顺序列出每个部分及其状态（**等待中**、**工作中**、**完成**、**失败**、**正在重试**或**失败了 2 次**），以及关于它的最新消息，或者它的成员现在在做什么。点击一个部分，可以打开它的成员的会话。**全部停止**在有成员工作时出现，会停止所有仍在工作的成员。
- **正在工作**：正在干活的成员，最多与你的集群规模相同。
- **帖子**（在宽屏上位于各部分旁边）：所有发布的内容，最新的在前，每条都显示它的类型（**计划**、**进展**、**完成**、**失败**、**发现**、**问题**、**备注**）以及它涉及的部分。

在战役中，发给所有人的帖子不会唤醒成员（完成了自己那部分的成员保持完成状态）；发给某个成员的消息会唤醒它。
