# Ανάπτυξη λογισμικού: CI, ζητήματα, εξαρτήσεις και περιστατικά

Οι πράκτορες μπορούν να φροντίζουν μια βάση κώδικα όσο εσείς κάνετε κάτι άλλο: να εξετάζουν μια αποτυχημένη εκτέλεση CI, να κάνουν διαλογή σε κάθε νέο ζήτημα, να κρατούν ενημερωμένες τις εξαρτήσεις και να ανταποκρίνονται σε μια ειδοποίηση, το καθένα ως προγραμματισμένη εργασία που φτιάχνεται από μια σύντομη φόρμα. Το **Βρείτε τι το χάλασε** του Git βάζει έναν πράκτορα να βρει το commit που χάλασε κάτι, και μια **Καμπάνια** χωρίζει μια μεγάλη αλλαγή σε μέρη που τα φτιάχνουν ταυτόχρονα πολλοί πράκτορες, ο καθένας σε δικό του worktree.

![Ρυθμίσεις → Προγραμματισμένες εργασίες: τα παραδείγματα της Ανάπτυξης λογισμικού](images/engineering.webp)

## Πώς λειτουργούν οι εργασίες ανάπτυξης λογισμικού

Οι τέσσερις εργασίες είναι παραδείγματα στις [Ρυθμίσεις → Προγραμματισμένες εργασίες](/settings?s=tasks) (**Ρυθμίσεις → Πράκτορες → Προγραμματισμένες εργασίες**), στο **Ξεκινήστε από ένα παράδειγμα** → **Ανάπτυξη λογισμικού**, δίπλα στο [**Έλεγχος νέων pull request**](/settings?s=tasks&find=Review%20new%20pull%20requests). Η καθεμία ανοίγει μια σύντομη φόρμα· συμπληρώστε την, επιλέξτε ποιος την εκτελεί στο **Εκτελείται από** και επιλέξτε **Δημιουργία εργασίας** (ή **Περισσότερες επιλογές…** για την πλήρη φόρμα εργασίας). Δείτε [Προγραμματισμένες εργασίες](/guide/tasks) για όλα όσα μπορεί να κάνει μια εργασία.

Τι έχουν κοινό:

- **Ένας φάκελος αποθετηρίου**: το αντίγραφο του αποθετηρίου σε αυτόν τον υπολογιστή από το οποίο δουλεύει ο πράκτορας. Το διαβάζει, και κάνει κάθε αλλαγή σε ένα νέο worktree (ένα ξεχωριστό αντίγραφο σε δικό του κλάδο), ώστε το δικό σας αντίγραφο και ο κλάδος του να μένουν ως έχουν.
- **Μια δεξιότητα η καθεμία**: ο πράκτορας ακολουθεί μια γραπτή μέθοδο, μια ενσωματωμένη δεξιότητα που μπορείτε να διαβάσετε και να αλλάξετε στις [Ρυθμίσεις → Δεξιότητες](/settings?s=skills): **ci-doctor**, **issue-triage**, **dependency-upgrades** και **incident-response**.
- **Τι επιτρέπεται να κάνει**: διακόπτες στη φόρμα, όπως το **Άνοιγμα πρόχειρου pull request με διόρθωση**. Για ό,τι αφήσετε ανενεργό, ο πράκτορας σας λέει τι θα είχε κάνει. Καμία από αυτές δεν κάνει ποτέ push στον προεπιλεγμένο κλάδο, force-push ή merge.
- **Webhooks**: ο Γιατρός CI, η Διαλογή ζητημάτων και η Πρώτη αντιμετώπιση περιστατικών ξεκινούν όταν μια υπηρεσία καλεί τη διεύθυνση της εργασίας. Μόλις φτιαχτεί η εργασία, η γραμμή της στη λίστα δείχνει τη διεύθυνση με ένα κουμπί αντιγραφής και, από κάτω, πού να την επικολλήσετε σε εκείνη την υπηρεσία («Στο αποθετήριο στο GitHub: Settings → Webhooks → Add webhook…»). Η φόρμα λέει το ίδιο πριν τη δημιουργήσετε. Ένα φίλτρο στην καθεμία αφήνει να ξεκινά εκτέλεση μόνο ό,τι την αφορά (μια αποτυχημένη εκτέλεση, ένα ζήτημα που μόλις άνοιξε, μια ειδοποίηση που δεν λέει ότι το πρόβλημα «επιλύθηκε»)· οι υπόλοιπες κλήσεις παίρνουν απάντηση και δεν ξεκινούν τίποτα. Το **Εκτέλεση τώρα** στο μενού μιας εργασίας (ή το **Δοκιμαστική εκτέλεση** στη φόρμα της) λειτουργεί χωρίς κλήση, για να τη δοκιμάσετε: ο Γιατρός CI παίρνει την τελευταία αποτυχημένη εκτέλεση, η Διαλογή ζητημάτων τα ζητήματα της τελευταίας ημέρας που δεν έχουν ετικέτες, και η Πρώτη αντιμετώπιση περιστατικών ελέγχει πώς τα πάει η υπηρεσία.
- **Πρόσβαση**: ο πράκτορας δουλεύει με το GitHub μέσω της εντολής gh όταν είναι συνδεδεμένη σε αυτόν τον υπολογιστή, και αλλιώς μέσω ενός κλειδιού στο θησαυροφυλάκιό σας ή μιας συνδεδεμένης εφαρμογής (GitHub, GitLab, Buildkite, CircleCI, Sentry, Grafana, Datadog, Better Stack: δείτε [Συνδεδεμένες εφαρμογές, κλειδιά και εργαλεία](/guide/connections)). Όταν χρειάζεται ένα κλειδί που δεν έχει, σας το ζητά.
- **Κάθε εκτέλεση** αναφέρει πώς πήγε σε μία γραμμή, στην ειδοποίησή της και στο ιστορικό της εργασίας, και κρατά σημειώσεις για την επόμενη εκτέλεση (τις ασταθείς δοκιμές που είδε, τις αναβαθμίσεις που ανέβαλε, τα περιστατικά ως τώρα). Μια εκτέλεση που χρειάζεται την έγκρισή σας την περιμένει, στη συνεδρία της και στα [Εισερχόμενα](/guide/inbox). Μπορεί να μην παρακολουθεί κανείς όταν ξεκινά μια εκτέλεση, οπότε για αυτές τις εργασίες επιλέξτε, στο **Περισσότερες επιλογές…** → **Δικαιώματα**, μια λειτουργία που αφήνει τα συνηθισμένα βήματα να προχωρούν και ρωτά για τα επικίνδυνα (**Αυτόματα**), αλλιώς η εκτέλεση θα σας περιμένει στην πρώτη της εντολή.

## Γιατρός CI

Μια αποτυχημένη εκτέλεση στο GitHub Actions, στο GitLab CI, στο Buildkite ή στο CircleCI ξυπνά έναν πράκτορα. Διαβάζει τα αρχεία καταγραφής των εργασιών που απέτυχαν και βρίσκει το πρώτο πραγματικό σφάλμα, κοιτάζει τις πρόσφατες εκτελέσεις της ίδιας εργασίας για να ξεχωρίσει μια ασταθή αποτυχία από μια πραγματική, την αναπαράγει σε ένα worktree, και μετά ενεργεί όπως του επιτρέψατε και τη συνοψίζει σε λίγες γραμμές.

### Ρυθμίστε τον

1. Στις [Ρυθμίσεις → Προγραμματισμένες εργασίες](/settings?s=tasks), επιλέξτε [**Γιατρός CI**](/settings?s=tasks&find=CI%20doctor) στην **Ανάπτυξη λογισμικού**.
2. Επιλέξτε τον **Φάκελο αποθετηρίου** και το **CI**: **GitHub Actions**, **GitLab CI**, **Buildkite** ή **CircleCI**.
3. Επιλέξτε τι επιτρέπεται να κάνει:
   - **Επανεκτέλεση εργασιών που μοιάζουν ασταθείς** (αρχικά ενεργό): μία φορά, όταν τα στοιχεία δείχνουν ότι απέτυχε η εκτέλεση και όχι ο κώδικας (μια λήξη χρόνου αναμονής, μια λήψη που απέτυχε, μια δοκιμή που είναι γνωστό ότι άλλοτε περνά κι άλλοτε όχι).
   - **Άνοιγμα πρόχειρου pull request με διόρθωση** (ενεργό): για μια πραγματική αποτυχία, η μικρότερη δυνατή διόρθωση σε δικό της κλάδο, αφού τρέξει η δοκιμή που αποτύγχανε, ως πρόχειρο για να το δείτε.
   - **Σχόλιο στο commit ή στο pull request** (ανενεργό): ένα σύντομο σχόλιο με την αιτία και τη διόρθωση ή το επόμενο βήμα.
4. Επιλέξτε **Δημιουργία εργασίας**. Η εργασία παίρνει το όνομα του CI της, π.χ. «Γιατρός CI · GitHub Actions».
5. Αντιγράψτε τη διεύθυνσή της από τη γραμμή της στο CI, όπως λέει η γραμμή κάτω από τη διεύθυνση:
   - **GitHub Actions**: **Settings → Webhooks → Add webhook** του αποθετηρίου· η διεύθυνση ως Payload URL, application/json, και μόνο το **Workflow runs** κάτω από τα μεμονωμένα συμβάντα (individual events).
   - **GitLab CI**: **Settings → Webhooks → Add new webhook** του έργου, μόνο με το **Pipeline events**.
   - **Buildkite**: **Settings → Notification Services**, **Add** στο Webhook, με το συμβάν build.finished.
   - **CircleCI**: **Project Settings → Webhooks → Add Webhook** του έργου, με το **Workflow Completed**.

Μόνο μια αποτυχημένη εκτέλεση τον ξεκινά (στο GitHub, μια εκτέλεση workflow με conclusion failure· στο GitLab, στο Buildkite και στο CircleCI, μια εκτέλεση με status failed). Κάθε εκτέλεση της εργασίας παίρνει τα βασικά στοιχεία της εκτέλεσης CI (το workflow, τη διεύθυνσή του, τον κλάδο, το commit και το μήνυμά του, το pull request), και η αναφορά της σε μία γραμμή λέει αν η αποτυχία ήταν ασταθής ή πραγματική, την αιτία και τι έκανε: «Ασταθής: λήξη χρόνου αναμονής του registry στο npm ci· εκτελέστηκε ξανά», ή «Πραγματική: ο αναλυτής ημερομηνιών χαλάει στα δίσεκτα έτη· πρόχειρο pull request #42».

## Διαλογή ζητημάτων

Κάθε ζήτημα που ανοίγει στο GitHub (ή στο Gitea) ξυπνά έναν πράκτορα που κάνει τη διαλογή του: διαβάζει το ζήτημα και τον οδηγό συνεισφοράς του έργου, του βάζει ετικέτες από αυτές που έχει το αποθετήριο, ψάχνει το ίδιο πρόβλημα στα ανοιχτά και στα πρόσφατα κλεισμένα ζητήματα με διάφορες διατυπώσεις (λέγοντας πόσο σίγουρος είναι), ζητά ευγενικά σε ένα σχόλιο από αυτόν που το ανέφερε ό,τι λείπει από την αναφορά (την έκδοση, τα βήματα, τα αρχεία καταγραφής) και, όταν η διόρθωση είναι μικρή και σαφής, τη δοκιμάζει σε ένα worktree και ανοίγει ένα πρόχειρο pull request που παραπέμπει στο ζήτημα.

1. Επιλέξτε [**Διαλογή ζητημάτων**](/settings?s=tasks&find=Issue%20triage) στην **Ανάπτυξη λογισμικού**.
2. Επιλέξτε τον **Φάκελο αποθετηρίου** και τι επιτρέπεται να κάνει: **Προσθήκη ετικέτας**, **Σχολιασμός** και **Δοκιμή των εύκολων ως πρόχειρα pull request** (όλα ενεργά αρχικά).
3. Επιλέξτε **Δημιουργία εργασίας** και μετά αντιγράψτε τη διεύθυνσή της στο **Settings → Webhooks → Add webhook** του αποθετηρίου στο GitHub, μόνο με το **Issues** κάτω από τα μεμονωμένα συμβάντα (στο Gitea: συμβάντα Issues).

Μόνο ένα ζήτημα που μόλις άνοιξε ξεκινά εκτέλεση. Ο πράκτορας δεν κλείνει, δεν κλειδώνει, δεν μεταφέρει και δεν διαγράφει ποτέ ένα ζήτημα (σε ένα σίγουρο διπλότυπο βάζει ετικέτα και αφήνει έναν συντηρητή να το κλείσει), δεν αναθέτει ποτέ ζητήματα σε ανθρώπους, και τηρεί ό,τι επιτρέπει το έργο: ένα έργο που δεν δέχεται pull request φτιαγμένα με τεχνητή νοημοσύνη δεν παίρνει κανένα. Ένα πρόβλημα ασφαλείας που αναφέρθηκε δημόσια δεν συζητιέται εκεί: ο πράκτορας παραπέμπει αυτόν που το ανέφερε στον ιδιωτικό τρόπο αναφοράς του έργου και σας ενημερώνει αμέσως.

## Κηπουρός εξαρτήσεων

Μία φορά την εβδομάδα ο πράκτορας φροντίζει τις εξαρτήσεις του αποθετηρίου (npm, pnpm, yarn, pip, uv, poetry, cargo και go): τι είναι παρωχημένο και ποιες έχουν δελτία ασφαλείας. Πρώτα έρχονται οι διορθώσεις ασφαλείας· μετά οι αναβαθμίσεις patch, minor και major, κάθε ομάδα χωριστά, και οι major δεν ανακατεύονται ποτέ με τις υπόλοιπες. Κάθε ομάδα γίνεται σε δικό της worktree, αφού διαβαστούν οι σημειώσεις έκδοσης όσων άλλαξαν για αλλαγές που σπάνε τη συμβατότητα και τρέξουν οι δοκιμές. Μια αναβάθμιση που χαλάει τις δοκιμές αναβάλλεται, με τον λόγο στις σημειώσεις της εργασίας, ώστε να μην προτείνεται ξανά κάθε εβδομάδα.

1. Επιλέξτε [**Κηπουρός εξαρτήσεων**](/settings?s=tasks&find=Dependency%20gardener) στην **Ανάπτυξη λογισμικού**.
2. Επιλέξτε τον **Φάκελο αποθετηρίου**, τη μέρα (αρχικά Δευτέρα) και την ώρα στο **Στις** (09:00).
3. **Άνοιγμα pull request** (ενεργό): ένα πρόχειρο pull request για κάθε ομάδα της οποίας οι δοκιμές περνούν, με τα σημαντικότερα, τα δελτία ασφαλείας που διορθώνει και τι να προσέξετε. Αν είναι ανενεργό, δεν κάνει push τίποτα και αναφέρει κάθε ομάδα με τις εντολές που την εφαρμόζουν.
4. Επιλέξτε **Δημιουργία εργασίας**.

Μια εβδομάδα όπου όλα είναι ενημερωμένα και δεν υπάρχει ανοιχτό δελτίο ασφαλείας περνά σιωπηλά.

## Πρώτη αντιμετώπιση περιστατικών

Μια ειδοποίηση από το Sentry, το Grafana, το Datadog, το Better Stack ή άλλη υπηρεσία ξυπνά έναν πράκτορα. Μέσα σε λίγα λεπτά σας στέλνει μια ειδοποίηση με το τι δεν πάει καλά, από πότε και πόσο σοβαρό είναι. Μετά βάζει τα σφάλματα, τα αρχεία καταγραφής, τις πρόσφατες αναπτύξεις και τις αλλαγές από την τελευταία καλή έκδοση σε ένα χρονολόγιο, βρίσκει την πιθανή αιτία με τα στοιχεία της και προτείνει το ασφαλέστερο βήμα, συνήθως μια επαναφορά. Δεν κάνει ποτέ επαναφορά, επανεκκίνηση ή ανάπτυξη χωρίς το ναι σας: ρωτά με μια κάρτα στη συνεδρία της εκτέλεσης, και όταν δεν απαντήσει κανείς εγκαίρως, η εκτέλεση αναφέρει ότι σας χρειάζεται, με την εντολή να περιμένει. Όταν όλα τελειώσουν, ζητήστε του στην ίδια συνεδρία την ανάλυση του περιστατικού (postmortem).

1. Επιλέξτε [**Πρώτη αντιμετώπιση περιστατικών**](/settings?s=tasks&find=Incident%20first%20responder) στην **Ανάπτυξη λογισμικού**.
2. Στο **Ο φάκελος του αποθετηρίου της υπηρεσίας** επιλέξτε τον φάκελό του, και στο **Οι ειδοποιήσεις έρχονται από** την υπηρεσία: **Sentry**, **Grafana**, **Datadog**, **Better Stack** ή **Άλλη υπηρεσία**.
3. **Πώς γίνεται η επαναφορά** (προαιρετικό): μια εντολή που μπορεί να τρέξει ο πράκτορας μόλις πείτε ναι, όπως `kubectl rollout undo deployment/web`. Αν μείνει κενό, σας ρωτά πώς.
4. Επιλέξτε **Δημιουργία εργασίας** και μετά στείλτε τις ειδοποιήσεις της υπηρεσίας στη διεύθυνσή της, όπως λέει η γραμμή της:
   - **Sentry**: **Settings → Developer Settings → Create New Integration → Internal Integration**, η διεύθυνση ως Webhook URL και το **Alert Rule Action** ενεργό· μετά προσθέστε την ενσωμάτωση στις ενέργειες των alert rules σας.
   - **Grafana**: **Alerting → Contact points → Add contact point**, η ενσωμάτωση Webhook με τη διεύθυνση· μετά στείλτε εκεί τις ειδοποιήσεις από μια notification policy.
   - **Datadog**: **Integrations → Webhooks → New**, με τη διεύθυνση και με το `"transition": "$ALERT_TRANSITION"` προσθεμένο στο payload του· μετά αναφέρετε το `@webhook-` και το όνομά του στα μηνύματα των monitors σας.
   - **Better Stack**: **Incidents → Integrations → Exporting data → Outgoing webhooks → Configure**, μετά **Add** στο Incident, μόνο με τα συμβάντα για περιστατικό που δημιουργήθηκε ή άνοιξε ξανά.

Οι ειδοποιήσεις ότι ένα πρόβλημα επιλύθηκε ή αποκαταστάθηκε δεν ξεκινούν τίποτα (του Sentry, του Grafana και του Datadog, χάρη στο φίλτρο)· όσες περάσουν παρ’ όλα αυτά σημειώνονται στις σημειώσεις της εργασίας και περνούν σιωπηλά. Με μια συνδεδεμένη εφαρμογή για την υπηρεσία ειδοποιήσεων, ο πράκτορας διαβάζει μέσα από αυτήν τα σφάλματα και τα αρχεία καταγραφής.

## Βρείτε τι το χάλασε

Όταν κάτι λειτουργούσε σε μια προηγούμενη έκδοση και τώρα είναι χαλασμένο, ένας πράκτορας μπορεί να βρει το commit που το χάλασε: δοκιμάζει τα commit ανάμεσα με το git bisect, χωρίζοντάς τα στη μέση κάθε φορά (χίλια commit θέλουν περίπου δέκα δοκιμές), κατονομάζει το πρώτο κακό commit και εξηγεί τι στην αλλαγή του χάλασε τα πράγματα και γιατί.

1. Στη [σελίδα Git](/git), ανοίξτε το αποθετήριο και το **Ιστορικό** του.
2. Ανοίξτε το commit όπου λειτουργούσε τελευταία φορά και επιλέξτε **Βρείτε τι το χάλασε** στο μενού ⋯ του, ή επιλέξτε το κουμπί **Βρείτε τι το χάλασε** δίπλα στο **Εύρεση commit** στην κορυφή της λίστας.
3. Στη φόρμα **Βρείτε τι το χάλασε**:
   - **Λειτουργούσε στο**: το commit από το οποίο την ανοίξατε (με την ετικέτα του, όταν έχει), αλλιώς η πιο πρόσφατη ετικέτα. Πληκτρολογήστε οποιαδήποτε ετικέτα, κλάδο ή commit· οι πιο πρόσφατες ετικέτες προτείνονται καθώς πληκτρολογείτε. Από κάτω εμφανίζεται το commit στο οποίο αντιστοιχεί, με το μήνυμα και την ηλικία του, ή «Δεν υπάρχει commit ή ετικέτα με αυτό το όνομα».
   - **Δεν λειτουργεί στο**: αρχικά `HEAD` (το πιο πρόσφατο commit στον κλάδο όπου βρίσκεστε).
   - **Τι δεν λειτουργεί**: με δικά σας λόγια, όσο πιο συγκεκριμένα μπορείτε («Η εξαγωγή ενός εγγράφου με εικόνες σε PDF αποτυγχάνει με “image too large”»).
   - **Πώς να ελεγχθεί (προαιρετικό)**: μια εντολή που αποτυγχάνει όσο το πρόβλημα υπάρχει, όπως `npm test -- export`. Χωρίς αυτήν, ο πράκτορας γράφει δικό του έλεγχο.
   - **Εκτελείται από**: ο πράκτορας, με το μοντέλο και τα δικαιώματα που χρησιμοποιήσατε τελευταία μαζί του στην αρχική σελίδα.
4. Επιλέξτε **Έναρξη**. Το κουμπί περιμένει μέχρι και τα δύο άκρα να είναι commit, όχι το ίδιο, και να έχει συμπληρωθεί το **Τι δεν λειτουργεί**.

Μια νέα συνεδρία ανοίγει αμέσως, σε ένα νέο worktree του αποθετηρίου, ώστε το δικό σας αντίγραφο να μένει ως έχει. Ο πράκτοράς της ακολουθεί τη δεξιότητα **git-bisect**: γράφει ένα μικρό script ελέγχου (τελειώνει με 0 όταν λειτουργεί, με 1 όταν είναι χαλασμένο, με 125 για ένα commit που δεν μπορεί να ελέγξει, όπως ένα που δεν γίνεται build), το δοκιμάζει πρώτα και στα δύο άκρα, τρέχει το `git bisect run` με αυτό, και μετά δείχνει το πρώτο κακό commit και το μέρος της αλλαγής του που χάλασε τα πράγματα, το αποδεικνύει αναιρώντας μόνο εκείνο το commit και προτείνει μια διόρθωση. Δεν αλλάζει τίποτα στους κλάδους σας. Όταν τελειώσετε, το μενού της συνεδρίας → **Ολοκλήρωση: τέλος για τώρα** προσφέρεται να αφαιρέσει το worktree της (δείτε [Εργασία σε worktree](/guide/sessions#work-in-a-worktree)).

Το πλαίσιο αναζήτησης (Ctrl+K) βρίσκει κι αυτό το **Βρείτε τι το χάλασε**: ανοίγει τη φόρμα για το αποθετήριο που χρησιμοποιήσατε τελευταίο.

## Καμπάνιες: μια μεγάλη αλλαγή σε πολλά μέρη

Μια καμπάνια κάνει μια μεγάλη, κυρίως μηχανική αλλαγή σε όλη μια βάση κώδικα (μεταφορά κάθε πακέτου σε νέο logger, αναβάθμιση ενός framework, μετονομασία ενός API παντού) με πολλούς πράκτορες ταυτόχρονα. Ένας επικεφαλής πράκτορας χωρίζει την αλλαγή σε μέρη (πακέτα, modules, φακέλους), και τα μέλη φτιάχνουν το καθένα ένα μέρος σε δικό του worktree, με τις δοκιμές του. Είναι το δεύτερο είδος [Σμήνους](/guide/research#set-a-swarm-on-a-hard-problem): μία ρύθμιση, το **Μέγεθος σμήνους**, λέει πόσα μέλη δουλεύουν ταυτόχρονα και στα δύο.

### Ξεκινήστε μία

1. Στην αρχική σελίδα, επιλέξτε τον φάκελο του αποθετηρίου. Μια καμπάνια χρειάζεται αποθετήριο git.
2. Ανοίξτε τις **Επιλογές**, επιλέξτε **Σμήνος** και διαλέξτε **Καμπάνια** («Μια μεγάλη αλλαγή σε μέρη, το καθένα σε δικό του worktree»).
3. Πείτε ποια είναι η αλλαγή και πώς ελέγχεται («Μετάφερε κάθε πακέτο από το Jest στο Vitest· το npm test πρέπει να περνά στο καθένα») και πατήστε **Έναρξη**.

Η σειρά Σμήνος γράφει «Καμπάνια · 5 ταυτόχρονα» (το μέγεθος του σμήνους σας). Όπως και με το σμήνος, δεν διατηρείται για την επόμενη συνεδρία σας, και μια σε βάθος έρευνα και μια καμπάνια δεν μπορούν να είναι ενεργές μαζί. Ένα όριο δαπανών που ορίζεται στο ίδιο μενού καλύπτει τον επικεφαλής και κάθε μέλος. Η φόρμα επεξεργασίας μιας προγραμματισμένης εργασίας έχει την ίδια επιλογή.

### Πώς λειτουργεί

1. Ο επικεφαλής ξεκαθαρίζει την αλλαγή και πώς ελέγχεται, και τη χωρίζει σε μέρη που το καθένα μπορεί να γίνει και να ελεγχθεί μόνο του. Αναρτά το σχέδιο στον πίνακα: τα μέρη, με το όνομά τους, με τη σειρά που πρέπει να γίνουν (πρώτα ο κοινός κώδικας).
2. Ξεκινά ένα μέλος για κάθε μέρος, το πολύ τόσα ταυτόχρονα όσο το μέγεθος του σμήνους σας, και το επόμενο καθώς τελειώνουν άλλα. Κάθε μέλος δουλεύει σε δικό του κλάδο, σε ένα νέο worktree που φτιάχνεται από τον κλάδο όπου βρίσκεται ο φάκελος του επικεφαλής.
3. Ένα μέλος αλλάζει μόνο το μέρος του, τρέχει τους ελέγχους του, κάνει commit στον κλάδο του και αναρτά το μέρος του ως ολοκληρωμένο (με τον κλάδο και τους ελέγχους) ή ως αποτυχημένο (με το τι πήγε στραβά).
4. Ένα μέρος που απέτυχε δοκιμάζεται μία ακόμα φορά, με όσα έμαθε η πρώτη προσπάθεια. Αν αποτύχει ξανά, μένει αποτυχημένο.
5. Ο επικεφαλής συγχωνεύει τους ολοκληρωμένους κλάδους στον κλάδο όπου δουλεύει, έναν τη φορά με μια λογική σειρά, τρέχοντας τους ελέγχους μετά από κάθε συγχώνευση, και αφαιρεί το worktree κάθε μέρους που συγχωνεύτηκε. Αν ζητήσετε pull request στο μήνυμά σας, ανοίγει αντί γι’ αυτό ένα για κάθε μέρος και δεν συγχωνεύει τίποτα. Δεν κάνει ποτέ push στον προεπιλεγμένο κλάδο.
6. Στο τέλος αναφέρει τι άλλαξε, τι απέτυχε και γιατί, και τι μένει να γίνει με το χέρι.

Για να μείνει όλη η αλλαγή σε δικό της κλάδο, ενεργοποιήστε το **Νέο worktree** στο μενού του φακέλου και για τον επικεφαλής: τα μέλη τότε ξεκινούν τους κλάδους τους από τον κλάδο του επικεφαλής, και οι συγχωνεύσεις καταλήγουν εκεί.

### Παρακολουθήστε την: η γραμμή και ο πίνακας

Η συνεδρία του επικεφαλής έχει μια γραμμή πάνω από το πλαίσιο μηνύματος: **Καμπάνια** · «σχεδιάζει τα μέρη της» στην αρχή, μετά «ολοκληρώθηκαν 12 από 40 μέρη · 2 με αποτυχία · 3 σε εξέλιξη», και **Κατάταξη**. Η συνεδρία κάθε μέλους έχει κι αυτή μια γραμμή: «Στην καμπάνια» και τον τίτλο του επικεφαλής, με **Κατάταξη** και **Επικεφαλής**. Στην πλευρική στήλη τα μέλη βρίσκονται κάτω από τον επικεφαλής, μαζεμένα σε μια γραμμή όπως «40 μέλη καμπάνιας · 3 σε εξέλιξη».

Το **Κατάταξη** ανοίγει τον **Πίνακα καμπάνιας** (από το κάτω μέρος της οθόνης στο κινητό):

- **Μέρη**: πόσα ολοκληρώθηκαν και πόσα απέτυχαν, και μετά κάθε μέρος με τη σειρά του σχεδίου, με το πού βρίσκεται (**Σε αναμονή**, **Εργάζεται**, **Τέλος**, **Απέτυχε**, **Δοκιμάζει ξανά** ή **Απέτυχε 2 φορές**) και το πιο πρόσφατο νέο του, ή τι κάνει τώρα το μέλος του. Κάντε κλικ σε ένα μέρος για να ανοίξετε τη συνεδρία του μέλους του. Το **Διακοπή όλων**, που εμφανίζεται όσο δουλεύουν μέλη, σταματά κάθε μέλος που δουλεύει ακόμα.
- **Εργάζεται τώρα**: τα μέλη που δουλεύουν, το πολύ όσο το μέγεθος του σμήνους σας.
- **Αναρτήσεις**, δίπλα στα μέρη σε φαρδιά οθόνη: ό,τι έχει αναρτηθεί, με τα νεότερα πρώτα, το καθένα με το είδος του (**Σχέδιο**, **Πρόοδος**, **Τέλος**, **Απέτυχε**, **Εύρημα**, **Ερώτηση**, **Σημείωση**) και το μέρος που αφορά.

Σε μια καμπάνια, οι αναρτήσεις προς όλους δεν ξυπνούν τα μέλη (ένα μέλος που τελείωσε το μέρος του μένει τελειωμένο)· ένα μήνυμα προς ένα μέλος το ξυπνά.

- «Γιατί απέτυχε η τελευταία εκτέλεση CI στο main του acme/shop; Ήταν ασταθής;»
- «Κάνε διαλογή στα ζητήματα που άνοιξαν στο acme/shop αυτή την εβδομάδα: βάλε τους ετικέτες και βρες τα διπλότυπα.»
- «Κάθε Δευτέρα στις 9, φρόντιζε τις εξαρτήσεις του ~/code/api και άνοιγε pull request για ό,τι περνά τις δοκιμές.»
- «Στήσε πρώτη αντιμετώπιση περιστατικών για τις ειδοποιήσεις του Grafana για το checkout, με επαναφορά μέσω kubectl rollout undo deployment/checkout.»
- «Γράψε την ανάλυση (postmortem) για τη χθεσινή διακοπή λειτουργίας του checkout.»
- «Λειτουργούσε στην v1.2.0: βρες τι χάλασε την εξαγωγή σε PDF στο ~/code/docs.»
- «Ξεκίνα μια καμπάνια στο ~/code/shop που μεταφέρει κάθε πακέτο από το Jest στο Vitest, με ένα pull request για κάθε πακέτο.»
