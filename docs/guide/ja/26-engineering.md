# エンジニアリング：CI、Issue、依存関係、インシデント

エージェントは、ほかの作業をしている間もコードベースの面倒を見てくれます。失敗したCIの実行の調査、新しいIssueのトリアージ、依存関係の最新化、アラートへの対応を、それぞれ短いフォームから作るスケジュールタスクとして任せられます。Gitの**壊した原因を探す**では、何かを壊したコミットをエージェントが見つけます。**キャンペーン**は、大きな変更をいくつかの部分に分け、複数のエージェントがそれぞれ専用のワークツリーで同時に進めます。

![設定 → スケジュールタスク：エンジニアリングの例](images/engineering.webp)

## エンジニアリングタスクの仕組み

4つのタスクは[設定 → スケジュールタスク](/settings?s=tasks)（**設定 → エージェント → スケジュールタスク**）の**例から始める**にある例です（**すべての例を表示**を押すと一覧が見られます）。[**新しいプルリクエストをレビュー**](/settings?s=tasks&find=Review%20new%20pull%20requests)の隣に並んでいます。どれも短いフォームが開きます。入力して、**実行のきっかけ**で実行する担当を選び、**タスクを作成**を選びます（タスクのフォームをすべて使うには**その他のオプション…**）。タスクでできることの詳細は[スケジュールタスク](/guide/tasks)をご覧ください。

どのタスクにも共通する点は次のとおりです。

- **リポジトリのフォルダ**：エージェントが作業の元にする、このコンピューター上のリポジトリのコピーです。エージェントはこれを読み取り、変更は新しいワークツリー（専用のブランチを持つ別のコピー）で行うため、手元のコピーとそのブランチはそのまま残ります。
- **それぞれに1つのスキル**：エージェントは、文書化された手順（組み込みのスキル）に従います。スキルは[設定 → スキル](/settings?s=skills)で読んだり変更したりできます。**ci-doctor**、**issue-triage**、**dependency-upgrades**、**incident-response**があります。
- **してよいこと**：フォームのスイッチで決めます。たとえば**修正を含むドラフトのプルリクエストを開く**です。オフにしたことについては、代わりに何をするつもりだったかをエージェントが伝えます。どのタスクも、デフォルトブランチへのプッシュ、強制プッシュ、マージは行いません。
- **Webhook**：CIドクター、Issueトリアージ、インシデント対応は、サービスがタスク専用のアドレスを呼び出すと始まります。タスクを作成すると、一覧の行にアドレスとコピーボタンが表示され、その下にそのサービスのどこに貼り付けるかが書かれています（「GitHubのリポジトリで：Settings → Webhooks → Add webhook…」）。作成前のフォームにも同じ説明があります。それぞれのフィルタにより、対象のものだけが実行を始めます（失敗した実行、新しく開かれたIssue、「解決済み」の通知ではないアラート）。それ以外には応答するだけで、何も始まりません。タスクのメニューの**今すぐ実行**（フォームでは**テスト実行**）なら、呼び出しなしで試せます。CIドクターは最新の失敗した実行を、Issueトリアージは直近1日のラベルのないIssueを、インシデント対応はサービスの状態を確認します。
- **アクセス**：エージェントは、このコンピューターでghコマンドにサインインしていればそれでGitHubを利用し、そうでなければ保管庫のキーか接続済みアプリ（GitHub、GitLab、Buildkite、CircleCI、Sentry、Grafana、Datadog、Better Stack。[接続済みアプリ、キー、ツール](/guide/connections)をご覧ください）を使います。持っていないキーが必要になると、エージェントが確認します。
- **実行ごと**に、どうなったかが1行で通知とタスクの履歴に報告され、次の実行のためのメモ（見かけた不安定なテスト、見送ったアップグレード、これまでのインシデント）も残されます。承認が必要な実行は、そのセッションと[受信トレイ](/guide/inbox)で承認を待ちます。実行が始まるとき、誰も見ているとは限りません。そのため、これらのタスクでは**その他のオプション…** → **権限**で、定型的な手順は進め、危険な手順は確認するモード（**自動**）を選んでください。そうしないと、最初のコマンドで実行が待機してしまいます。

## CIドクター

GitHub Actions、GitLab CI、Buildkite、CircleCIで実行が失敗すると、エージェントが起動します。失敗したジョブのログを読んで最初の本当のエラーを見つけ、同じジョブの最近の実行を見て不安定な失敗か本物の失敗かを判断し、ワークツリーで再現します。その後、許可された範囲で対応し、数行にまとめて報告します。

### 設定方法

1. [設定 → スケジュールタスク](/settings?s=tasks)で、**例から始める**（**すべての例を表示**）の[**CIドクター**](/settings?s=tasks&find=CI%20doctor)を選びます。
2. **リポジトリのフォルダ**と**CI**を選びます。**GitHub Actions**、**GitLab CI**、**Buildkite**、**CircleCI**のいずれかです。
3. してよいことを選びます。
   - **不安定そうなジョブを再実行**（初期設定はオン）：コードではなく実行のほうが失敗したと証拠から判断できるとき（タイムアウト、ダウンロードの失敗、出たり出なかったりすることが知られているテスト）に、1回だけ再実行します。
   - **修正を含むドラフトのプルリクエストを開く**（オン）：本物の失敗に対して、専用のブランチで最小限の修正を行い、失敗していたテストを実行したうえで、確認用のドラフトとして開きます。
   - **コミットまたはプルリクエストにコメントする**（オフ）：原因と、修正または次の手順を書いた短いコメントを1件付けます。
4. **タスクを作成**を選びます。タスクにはCIにちなんだ名前が付きます。たとえば「CIドクター · GitHub Actions」です。
5. アドレスの下の説明に従って、行にあるアドレスをCIにコピーします。
   - **GitHub Actions**：リポジトリの**Settings → Webhooks → Add webhook**で、アドレスをPayload URLに入れ、application/jsonを選び、個別のイベントでは**Workflow runs**だけを選びます。
   - **GitLab CI**：プロジェクトの**Settings → Webhooks → Add new webhook**で、**Pipeline events**だけを選びます。
   - **Buildkite**：**Settings → Notification Services**で、Webhookの**追加**を選び、イベントはbuild.finishedにします。
   - **CircleCI**：プロジェクトの**Project Settings → Webhooks → Add Webhook**で、**Workflow Completed**を選びます。

失敗した実行だけが起動のきっかけになります（GitHubでは結論がfailureのワークフロー実行、GitLab、Buildkite、CircleCIではステータスがfailedの実行）。実行ごとに、その実行の要点（ワークフロー、そのアドレス、ブランチ、コミットとそのメッセージ、プルリクエスト）が渡されます。1行の報告には、不安定か本物か、原因、行ったことが書かれます。たとえば「不安定：npm ciでレジストリがタイムアウト。再実行しました」「本物：日付パーサーがうるう年で壊れる。ドラフトのプルリクエスト #42」のようになります。

## Issueトリアージ

GitHub（またはGitea）でIssueが開かれるたびに、エージェントが起動してトリアージします。Issueとプロジェクトのコントリビューションガイドを読み、リポジトリにあるラベルを付けます。同じ問題が開いているIssueや最近閉じたIssueにないか、いくつかの言い回しで探します（確信度も伝えます）。報告に足りない情報（バージョン、手順、ログ）は、報告者に丁寧なコメントで尋ねます。修正が小さく明確な場合は、ワークツリーで試し、そのIssueを参照するドラフトのプルリクエストを開きます。

1. **例から始める**（**すべての例を表示**）で[**Issueトリアージ**](/settings?s=tasks&find=Issue%20triage)を選びます。
2. **リポジトリのフォルダ**と、してよいことを選びます。**ラベルを付ける**、**コメントする**、**簡単なものはドラフトのプルリクエストとして試す**です（初期設定はすべてオン）。
3. **タスクを作成**を選び、そのアドレスをGitHubのリポジトリの**Settings → Webhooks → Add webhook**にコピーします。個別のイベントでは**Issues**だけを選びます（GiteaではIssues events）。

新しく開かれたIssueだけが実行のきっかけになります。エージェントは、Issueを閉じたり、ロックしたり、移したり、削除したりしません（確実な重複にはラベルを付け、閉じるのはメンテナーに任せます）。担当者の割り当ても行わず、プロジェクトの方針も守ります。AIで作ったプルリクエストを受け付けないプロジェクトには、送りません。公開の場で報告されたセキュリティ上の問題は、その場では議論しません。エージェントは報告者にプロジェクトの非公開の報告方法を案内し、すぐにお知らせします。

## 依存関係ガーデナー

週に1回、エージェントがリポジトリの依存関係（npm、pnpm、yarn、pip、uv、poetry、cargo、go）を見直します。古くなっているもの、セキュリティ勧告が出ているものを調べます。優先されるのはセキュリティ修正で、その次にパッチ、マイナー、メジャーのアップグレードを、グループごとに分けて行います。メジャーはほかと混ぜません。各グループは専用のワークツリーで作られ、変更点のリリースノートを読んで破壊的変更を確認し、テストを実行します。テストが失敗するアップグレードは見送られ、毎週同じ提案をしないよう、理由がタスクのメモに残されます。

1. **例から始める**（**すべての例を表示**）で[**依存関係ガーデナー**](/settings?s=tasks&find=Dependency%20gardener)を選びます。
2. **リポジトリのフォルダ**、**オン**で曜日（初期設定は月曜日）、**時刻：**で時刻（9:00）を選びます。
3. **開いているプルリクエスト**（オン）：テストが通ったグループごとに、ドラフトのプルリクエストを1件作り、主な変更点、修正されるセキュリティ勧告、注意点を添えます。オフにすると何もプッシュせず、各グループを、適用するコマンドとともに報告します。
4. **タスクを作成**を選びます。

すべてが最新で、未対応のセキュリティ勧告もない週は、何も通知されません。

## インシデント初動対応

Sentry、Grafana、Datadog、Better Stack、または別のサービスからのアラートで、エージェントが起動します。数分以内に、何が問題で、いつからで、どのくらい深刻かが通知で届きます。続いて、エラー、ログ、最近のデプロイ、最後に正常だったリリース以降の変更を1つのタイムラインにまとめ、考えられる原因を根拠とともに見つけ、最も安全な対処（たいていはロールバック）を提案します。あなたの了承なしに、ロールバック、再起動、デプロイを行うことはありません。実行のセッションに表示されるカードで確認し、時間内に誰も答えなかった場合は、対応が必要であること、待機中のコマンドを報告します。終わったら、同じセッションで事後検証レポートを依頼できます。

1. **例から始める**（**すべての例を表示**）で[**インシデント初動対応**](/settings?s=tasks&find=Incident%20first%20responder)を選びます。
2. **サービスのリポジトリのフォルダ**と**アラートの送信元**を選びます。**Sentry**、**Grafana**、**Datadog**、**Better Stack**、**別のサービス**のいずれかです。
3. **ロールバックの方法**（任意）：了承した後にエージェントが実行してよいコマンドです。たとえば`kubectl rollout undo deployment/web`です。空欄の場合は、方法を尋ねられます。
4. **タスクを作成**を選び、その行の説明に従って、サービスのアラートの送信先をそのアドレスにします。
   - **Sentry**：**Settings → Developer Settings → Create New Integration → Internal Integration**で、アドレスをWebhook URLに入れ、**Alert Rule Action**をオンにします。その後、アラートルールのアクションにこのインテグレーションを追加します。
   - **Grafana**：**Alerting → Contact points → Add contact point**で、アドレスを指定したWebhookインテグレーションを作り、通知ポリシーからそこにアラートを送ります。
   - **Datadog**：**Integrations → Webhooks → New**で、アドレスを指定し、ペイロードに`"transition": "$ALERT_TRANSITION"`を追加します。その後、モニターのメッセージに`@webhook-`とその名前を入れます。
   - **Better Stack**：**Incidents → Integrations → Exporting data → Outgoing webhooks → Configure**を開き、Incidentの**追加**を選んで、インシデントの作成または再開のイベントだけを選びます。

問題が解決または回復したという通知では、何も始まりません（Sentry、Grafana、Datadogはフィルタによります）。それでも届いたものはタスクのメモに記録され、通知はされません。アラートを出すサービスの接続済みアプリがあれば、エージェントはそれを通じてエラーとログを読みます。

## 壊した原因を探す

以前のバージョンでは動いていたものが今は壊れているとき、エージェントがそれを壊したコミットを見つけられます。git bisectで間のコミットを試し、毎回半分に絞り込みます（1,000件のコミットなら約10回の試行）。最初に壊れたコミットを特定し、その変更のどこがなぜ問題を起こしたのかを説明します。

1. [Gitページ](/git)でリポジトリを開き、**履歴**を開きます。
2. 最後に動作していたコミットを開き、その⋯メニューから**壊した原因を探す**を選びます。または、一覧の上部にある**コミットを検索**の隣の**壊した原因を探す**ボタンを選びます。
3. **壊した原因を探す**フォームで入力します。
   - **動作していた時点**：開いたコミットです（タグがあればそのタグで表示されます）。ない場合は最新のタグになります。タグ、ブランチ、コミットを自由に入力できます。入力中には最新のタグが候補として表示されます。その下には、対応するコミットがメッセージと経過時間とともに表示されます。該当がなければ「No commit or tag by that name」と表示されます。
   - **壊れた時点**：初期値は`HEAD`です（現在のブランチの最新のコミット）。
   - **壊れている内容**：できるだけ具体的に、ご自身の言葉で書きます（「画像を含むドキュメントをPDFにエクスポートすると、『image too large』で失敗する」）。
   - **確認方法（任意）**：壊れている間は失敗するコマンドです。たとえば`npm test -- export`です。指定しない場合は、エージェントが独自の確認処理を作成します。
   - **実行のきっかけ**：エージェントです。モデルと権限は、スタートページで前回そのエージェントに使ったものになります。
4. **開始**を選びます。両端がどちらもコミットで、同じコミットではなく、**壊れている内容**が入力されるまで、選べません。

新しいセッションがすぐに開き、リポジトリの新しいワークツリーで作業します。手元のコピーはそのままです。エージェントは**git-bisect**スキルに従います。まず小さな確認スクリプトを書きます（動作すれば0、壊れていれば1、ビルドできないなどテストできないコミットには125で終了します）。それを両端で最初に試し、`git bisect run`で実行して、最初に壊れたコミットと、その変更のうち問題を起こした部分を示します。そのコミットだけを取り消して確かめ、修正を提案します。ブランチには何も変更を加えません。終わったら、セッションのメニュー → **完了にする：いったん終了**で、ワークツリーを削除するか確認されます（[ワークツリーで作業する](/guide/sessions#work-in-a-worktree)をご覧ください）。

検索ボックス（Ctrl+K）でも**壊した原因を探す**が見つかります。最後に使ったリポジトリを対象にしたフォームが開きます。

## キャンペーン：多数のパーツに分けた大きな変更

キャンペーンは、コードベース全体にわたる大きな変更（すべてのパッケージを新しいロガーに移す、フレームワークをアップグレードする、APIの名前をあらゆる場所で変更するなど）のうち、主に機械的な作業を、複数のエージェントで同時に行う機能です。リードエージェントが変更をパーツ（パッケージ、モジュール、フォルダ）に分け、メンバーがそれぞれ1つのパーツを、専用のワークツリーでテストとともに作成します。これは[スウォーム](/guide/research#set-a-swarm-on-a-hard-problem)の2つ目の種類で、同時に作業する数は、どちらも1つの設定**スウォームの規模**で決まります。

### 開始する

1. スタートページで、リポジトリのフォルダを選びます。キャンペーンにはGitリポジトリが必要です。
2. **オプション**を開き、**スウォーム**を選んで、**キャンペーン**（「1つの大きな変更を、パーツごとにワークツリーで」）を選びます。
3. 変更内容と確認方法（「すべてのパッケージをJestからVitestに移行する。各パッケージでnpm testが通ること」）を入力し、**開始**を押します。

スウォームの行には「キャンペーン · 5件同時」（スウォームの規模）と表示されます。スウォームと同様に、次のセッションには引き継がれません。また、ディープリサーチとキャンペーンを同時にオンにすることはできません。同じメニューで設定した支出上限は、リードとすべてのメンバーに適用されます。スケジュールタスクのエディタにも同じ選択肢があります。

### 仕組み

1. リードは変更内容と確認方法を整理し、それぞれ単独で実施・テストできるパーツに分けます。そして、パーツを名前付きで、実施する順（共有コードが先）にまとめたプランをボードに投稿します。
2. パーツごとにメンバーを開始します。同時に動くのはスウォームの規模までで、他のメンバーが終わるたびに次を開始します。各メンバーは、リードのフォルダがあるブランチから作られた新しいワークツリーで、専用のブランチを使って作業します。
3. メンバーは担当のパーツだけを変更し、確認を実行して、自分のブランチにコミットします。その後、パーツを完了（ブランチと確認結果を添えて）または失敗（問題の内容を添えて）として投稿します。
4. 失敗したパーツは、そこまでに分かったことを踏まえてもう1回やり直します。再び失敗した場合は、失敗のままになります。
5. リードは、完了したブランチを自分の作業中のブランチに、適切な順序で1つずつマージし、そのたびに確認を実行して、マージしたパーツのワークツリーを取り除きます。メッセージでプルリクエストを依頼した場合は、マージはせず、パーツごとにプルリクエストを作成します。デフォルトブランチにプッシュすることはありません。
6. 最後に、変更された内容、失敗した内容とその理由、手作業で残っている作業を報告します。

変更全体を専用のブランチにまとめるには、リードにもフォルダメニューの**新しいワークツリー**をオンにします。そうすると、メンバーはリードのブランチから分岐し、マージもそのブランチに反映されます。

### 進行を見る：バーとボード

リードのセッションでは、メッセージ欄の上にバーが表示されます。最初は**キャンペーン** · 「パーツを計画中」、その後は「40件中12件のパーツが完了 · 2件失敗 · 3件実行中」と表示され、**ボード**があります。各メンバーのセッションにもバーがあり、「次のキャンペーンに参加中」とリードのタイトルが表示され、**ボード**と**リード**があります。サイドバーでは、メンバーはリードの下に「キャンペーンメンバー40件 · 3件実行中」のような1行にまとめて表示されます。

**ボード**を開くと**キャンペーンボード**が表示されます（スマートフォンでは画面の下から表示されます）。

- **パーツ**：完了と失敗の件数に続き、プランの順に各パーツの状況（**待機中**、**実行中**、**完了**、**失敗**、**再試行中**、または**2回失敗**）と最新の状況、またはメンバーが今行っている作業が表示されます。パーツをクリックすると、そのメンバーのセッションが開きます。メンバーが作業している間は**すべて停止**があり、作業中のメンバーをすべて停止します。
- **作業中**：作業しているメンバーです。最大でスウォームの規模までです。
- **投稿**：広い画面ではパーツの横に表示されます。投稿されたすべての内容が新しい順に並び、それぞれに種類（**プラン**、**進捗**、**完了**、**失敗**、**発見**、**質問**、**メモ**）と、関係するパーツが表示されます。

キャンペーンでは、全員宛ての投稿でメンバーが起こされることはありません（パーツが完了したメンバーは完了のままです）。1人のメンバー宛てのメッセージは、そのメンバーを起こします。

## エージェントに頼んでみる
