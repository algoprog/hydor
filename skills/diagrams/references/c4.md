# Software architecture: the C4 levels

For explaining a software system to the people who build, run or pay for it. The C4 model
(c4model.com) draws one system at up to four levels of zoom, one diagram per level. Most teams need
only the first two.

| Level | Shows | For | Draw it? |
| --- | --- | --- | --- |
| 1. System context | the system as one box, the people who use it, the other systems it talks to | everyone, technical or not | almost always |
| 2. Container | inside the system: each app and data store that runs on its own, what it does, its technology, how they talk | developers, operations | usually |
| 3. Component | inside one container: its main parts and how they talk | that container's developers | only when it helps |
| 4. Code | classes and functions | | rarely; generated from the code if at all |

- **A container is anything that runs or stores data on its own:** a web app in the browser, a
  server app, a mobile or desktop app, a database, a file or object store, a serverless function, a
  script. Not a Docker container, though one may hold it.
- **Supporting views:** a system landscape (all of an organisation's systems together), a dynamic view
  (the steps of one feature: draw it as a sequence diagram), a deployment view (where the containers
  run: servers, cloud services, environments; `architecture-beta`, or a flowchart with a subgraph per
  environment).
- **Gather the facts from the code and its configuration,** not from memory: services and databases
  in compose or deployment files, the clients and the APIs they call, queues, the outside services
  called (the codebase-tour skill). Mark what you inferred and ask about it.

## What makes it readable

From the model's notation guidance:

- A title that names the kind of diagram and its scope: "Container diagram: online shop".
- A key for shapes, colours and line styles; acronyms spelled out.
- Every box says what kind of thing it is and, for containers and components, its technology
  (`[Container: Node.js]`), with a few words on what it does.
- Every line goes one way and is labelled with what it does ("Sends orders", not "Uses"); between
  containers, also how ("JSON over HTTPS").
- Colours mean the same in every diagram, and never alone: outside systems also get a dashed border.
- One level per diagram, and the same names in all of them.

## In Mermaid

Draw C4 views as flowcharts: a subgraph for the system's boundary, `[(…)]` for data stores, a
`classDef` with a dashed border for outside systems. Both examples render in Mermaid 12 with the page
in `references/mermaid.md`; put the key under the diagram as text ("Rounded: a person. Cylinder: a
data store. Dashed: outside the system.").

System context:

```
---
config:
  flowchart:
    wrappingWidth: 320
---
flowchart TB
  accTitle: System context diagram for the online shop
  accDescr: Customers order from the online shop; staff manage it; it uses a payment provider and an email service.
  customer(["Customer<br>[Person]<br>Orders coffee online"])
  staff(["Shop staff<br>[Person]<br>Pack and send orders"])
  shop["Online shop<br>[Software system]<br>Takes orders and payments"]
  pay["Payment provider<br>[Software system, external]<br>Charges cards"]
  mail["Email service<br>[Software system, external]<br>Sends receipts"]
  customer -- "Browses and orders" --> shop
  staff -- "Manages orders and stock" --> shop
  shop -- "Charges cards" --> pay
  shop -- "Sends receipts through" --> mail
  classDef ext stroke-dasharray: 5 5
  class pay,mail ext
```

Container:

```
---
config:
  flowchart:
    wrappingWidth: 320
---
flowchart TB
  accTitle: Container diagram for the online shop
  accDescr: The customer uses the web shop in a browser; it calls the API, which keeps orders in PostgreSQL and asks the payment provider to charge cards.
  customer(["Customer<br>[Person]"])
  subgraph shop["Online shop [Software system]"]
    web["Web shop<br>[Container: React]<br>Product pages, basket"]
    api["API<br>[Container: Node.js]<br>Orders and payments"]
    db[("Database<br>[Container: PostgreSQL]<br>Orders, customers")]
  end
  pay["Payment provider<br>[Software system, external]"]
  customer -- "Browses and orders<br>(HTTPS)" --> web
  web -- "Sends orders<br>(JSON over HTTPS)" --> api
  api -- "Reads and writes<br>(SQL)" --> db
  api -- "Charges cards<br>(HTTPS)" --> pay
  classDef ext stroke-dasharray: 5 5
  class pay ext
```

- `wrappingWidth: 320` keeps each label's lines as written; without it Mermaid wraps them into narrow
  boxes.
- The arrow into the boundary may run through the boundary's title; it stays readable. Keep the
  diagram top-down: a boundary's own `direction` is ignored once its boxes link outside it.
- Mermaid's own C4 syntax (`C4Context`, `C4Container`) is marked experimental. Tried in Mermaid 12, it
  kept its own blues instead of the page's colours, drew small text and left wide empty areas. Use it
  only when the person's tool expects it.
- A team that keeps its architecture in its repository and wants every level drawn from one model
  can use Structurizr's DSL, the C4 model's own tool; for most, these flowcharts are enough.
